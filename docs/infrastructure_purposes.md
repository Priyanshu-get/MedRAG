# MedRAG Infrastructure & Stack Purpose Guide

This document explains the technical purpose, architectural role, and advantages of every key software component in the **MedRAG** infrastructure stack (including Docker, Redis, Qdrant, PostgreSQL + pgvector, and Celery).

---

## 🐋 1. Docker & Docker Compose
*   **What it is**: A containerization platform that packages applications and their dependencies into self-contained units.
*   **Role in MedRAG**: Hosts and coordinates the database and caching stack (**Qdrant**, **PostgreSQL**, and **Redis**).
*   **Why it is used**:
    1.  **Eliminates "Works on My Machine" Syndrome**: Installing vector databases and custom PostgreSQL extensions (like `pgvector`) natively on host operating systems (macOS, Windows, Linux) is highly error-prone and tedious. Docker handles this compilation inside a standardized Linux layer.
    2.  **Instant Orchestration**: With a single command (`docker-compose up -d`), three highly complex, independent server systems are launched and interconnected inside a secure, shared virtual network.
    3.  **Data Persistence**: Uses Docker Volumes (`qdrant_data`, `postgres_data`, `redis_data`) to ensure that medical literature indexed in the databases is not deleted when the containers stop or update.

---

## ⚡ 2. Redis (Cache & Task Queue)
*   **What it is**: An ultra-fast, in-memory, key-value data store.
*   **Role in MedRAG**: Acts as the **Query Response Cache** and the **Message Broker** for Celery background tasks.
*   **Why it is used**:
    1.  **Response Caching (Zero LLM/Database Latency)**: 
        - Repeating the identical medical query (e.g., *"What is the standard dose of Metformin?"*) is common in clinical practice. 
        - Instead of running a 7-stage pipeline (costing Gemini API tokens and takes ~5 seconds of CPU time), the backend saves the generated JSON response in Redis with a Time-To-Live (TTL) of 1 hour.
        - Repeat requests bypass the database and LLMs completely, returning instantly (under `5ms`).
    2.  **Celery Message Broker**: Celery (which schedules tasks in the background) needs an extremely fast storage system to distribute, queue, and manage task signals. Redis acts as the queue broker that manages these scheduled literature-scraping jobs.

---

## 🔎 3. Qdrant (Vector Database)
*   **What it is**: A purpose-built, highly-optimized vector similarity database.
*   **Role in MedRAG**: Stores high-dimensional vector embeddings of chunked medical documents and performs dense semantic search.
*   **Why it is used**:
    1.  **Semantic Similarity**: Traditional databases search by matching keywords. Qdrant searches by *concepts*. If a query asks for "high blood pressure guidelines" and an article contains "hypertension management recommendations," Qdrant retrieves it because the underlying math vectors generated by `BAAI/bge-small` are conceptually close in 384-dimensional space.
    2.  **Cosine Distance Math**: Specifically optimized to perform millions of high-speed matrix multiplications to rank retrieved excerpts based on cosine similarity in milliseconds.

---

## 📚 4. PostgreSQL + `pgvector`
*   **What it is**: A robust relational database extended with `pgvector` (vector similarity features) and standard full-text indexing.
*   **Role in MedRAG**: Stores structured medical publication metadata (authors, journal titles, publication dates, PMIDs, DOIs) and executes sparse keyword searching.
*   **Why it is used**:
    1.  **Hybrid Retrieval (RRF)**: 
        - Vector search (Qdrant) is great for concepts, but struggles with highly specific technical terms, exact acronyms, or specific drug dosages (e.g., *"COVID-19 vaccine mRNA-1273"*).
        - PostgreSQL full-text search (sparse index) excels at exact matches.
        - MedRAG combines both using **Reciprocal Rank Fusion (RRF)** to get the ultimate precision.
    2.  **Relational Integrity**: Managing medical disclaimers, user chat records, source citations, and ingest logging is highly structured and requires a reliable relational database (SQL) with strict ACID transactions.

---

## 🔄 5. Celery & Celery Beat (Task Scheduler)
*   **What it is**: An asynchronous distributed task queue and scheduler.
*   **Role in MedRAG**: Orchestrates the automated weekly medical literature updates.
*   **Why it is used**:
    1.  **Non-Blocking API Calls**: Scraping PubMed or PMC for 50 detailed research papers, cleaning the HTML, chunking, embedding, and indexing can take minutes. If the main FastAPI thread ran this task, the API would hang, and the web interface would appear frozen. Celery offloads this to background worker threads.
    2.  **Automated Recurrence (Celery Beat)**: Configured to run every Sunday at 02:00 UTC. It checks for new peer-reviewed publications on 16 pre-selected chronic conditions and automatically pulls, processes, and index-seeds the literature database to keep the RAG assistant current.

## 🧠 Summary Table: Stack Alignment

| Infrastructure | Categorization | Architectural Problem it Solves | Impact on MedRAG Assistant |
|---|---|---|---|
| **Docker** | Containerization | Environmental inconsistencies & complex multi-service local setups. | Instant, one-command deployment of the database stack. |
| **Redis** | In-Memory Cache | Repeated queries wasting LLM API fees and database query processing time. | Under `5ms` response time on cached queries; powers Celery tasks. |
| **Qdrant** | Vector Store | Understanding user query concepts instead of raw matching words. | Enables concept-level matching (e.g., matching "metformin" with "biguanides"). |
| **PostgreSQL** | Relational DB | Precise tracking of exact drug names, dosages, publication dates, and PMIDs. | Hybrid search (concept + keyword) prevents false positive vectors. |
| **Celery** | Task Worker | Preventing time-consuming web scrapers from blocking live chat queries. | Allows seamless automated weekly indexing without server lag. |
